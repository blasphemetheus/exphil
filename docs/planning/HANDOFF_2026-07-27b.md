## READ FIRST — rules that save you from wasted sessions

1. **≥3 live RUNS per policy** (variance is in runs, not seeds — item 0a).
   Use `scripts/eval_live_protocol.sh` — it IS the protocol: refuses to run
   beside heavy jobs, logs loadavg, prints staleness, batch-scores.
2. **Never run live evals with training or the test suite active.** Under
   load the harness COLLAPSES (~1 fps, stuck at stage select). The protocol
   script guards this; don't FORCE=1 unless measuring the collapse itself.
3. **~16% stale sends is this laptop's STEADY state** during live runs
   (uniform 15.7–17.2% across loadavg 2–5). Comparisons are valid because
   it is uniform; treat outliers as measurement failures and discard.
4. **`ExPhil.Training.Output` writes to STDERR.** `2>/dev/null` on a mix
   script eats ALL its output silently (this bit the protocol script's own
   first run).
5. **The `mix` hazard is live here**: any `mix` invocation recompiles
   changed `.ex` files and kills a running training with SIGSEGV. Editing
   a `.sh` while a bash instance of it runs is also unsafe (bash reads
   lazily) — it survived once only because the file fits one read buffer.

### Scheduled sampling: IMPLEMENTED, TESTED, first policy trained

`ExPhil.Training.ScheduledSampling` (commit `25ddb5e`): swaps the last
window position's prev-action slice for the model's OWN decoded prediction
on P of samples; decode pinned to the live path; slice found empirically
(`Attribution.prev_action_dim_range/1`); ss_fn lives on the trainer
struct, never in config. Wired into BOTH `dagger_drill.exs` and the main
config.ex pipeline as `--scheduled-sampling P --ss-ramp N`. 6/6 new tests
green (`test/exphil/training/scheduled_sampling_test.exs`), full stale
suite green. Loss under SS is a harder objective — never compare loss
curves across the flag.

First SS policy: `checkpoints/ms_synth_ss.bin` = synth + prev-action +

frames, loss 0.001, 29 epochs). NOTE: plain synth (`ms_synth_a`) has NO
prev-action, so the comparison set is synth / synth+PA (`ms_pa_*`: 32.3 &

### SS × synth: MEASURED — first clean intervention win since synthesis

The 2x2 (full table + mechanism: EXPOSURE_BIAS.md item 6). Headline:

- `ms_synth_a` (no PA) vs IDLE opponent: **0/0/0** — crouches all game.
- `ms_pa_a` (PA, teacher-forced) vs IDLE: **0/0/0**, at the day's cleanest

- `ms_synth_ss` (PA + SS 0.5) vs IDLE: **90.6/90.1/92.5 self/min, chains
  4/4/6, zero hit-induced** — double its own vs-CPU rate, 1.03x run spread
  (vs 2.2x vs the CPU), and it scored this under 17–29% staleness.

Two measurement lessons landed with it: the eval OPPONENT is part of the
input distribution (idle-opponent evals only mean something for robust
policies — item 0c-5), and the earlier "16% staleness steady state" was
wrong — staleness is load-dependent, 1.6–30.8% across the day; it is a
per-run health stat, >10% = degraded run (item 0c-3 corrected).

Known hole: ms_synth_ss vs CPU (38.9–48.2, chains 2/3/3) was measured at
the day's WORST staleness (30%) — redo under clean conditions before
trusting that cell. Also single training run: replicate ms_synth_ss with
2 more seeds before building on it.
